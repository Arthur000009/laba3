# Сервис маршрутизации курьерской доставки (Dostavka API)

---

## 1. Предметная область и модель данных

Модель данных состоит из 5 взаимосвязанных сущностей, отображенных в таблицы PostgreSQL с ограничениями целостности на уровне СУБД (`init.sql`):

1. **`User` (`users`) — Пользователь (Клиент / Отправитель)**
    * Поля: `id` (PK), `name` (`NOT NULL`), `email` (`NOT NULL`, `UNIQUE`).
    * Роль: Создает отправления для доставки.

2. **`Shipment` (`shipments`) — Отправление (Посылка)**
    * Поля: `id` (PK), `created_at` (`NOT NULL`, генерируется сервером), `sender_id` (`FK -> users.id`, `ON DELETE CASCADE`), `address` (`NOT NULL`), `weight` (`NOT NULL`, `CHECK (weight > 0)`), `status` (`CHECK (status IN ('CREATED', 'ASSIGNED', 'IN_TRANSIT', 'DELIVERED', 'CANCELLED'))`).
    * Связь: Многие-к-одному (`@ManyToOne`) с сущностью `User`.

3. **`Route` (`routes`) — Маршрут курьера**
    * Поля: `id` (PK), `date` (`LocalDate / DATE`, `NOT NULL`), `max_weight` (`NOT NULL`, `CHECK (max_weight > 0)`), `status` (`CHECK (status IN ('PLANNED', 'IN_PROGRESS', 'COMPLETED'))`).
    * Роль: Определяет дату выезда, максимальную грузоподъемность транспорта и текущий этап выполнения рейса.

4. **`Stop` (`stops`) — Остановка маршрута**
    * Поля: `id` (PK), `route_id` (`FK -> routes.id`, `ON DELETE CASCADE`), `address` (`NOT NULL`), `sequence_number` (`NOT NULL`, `CHECK (sequence_number > 0)`).
    * Ограничения: Составной уникальный ключ `uk_stop_route_sequence (route_id, sequence_number)` гарантирует отсутствие дублирующихся порядковых номеров остановок внутри одного маршрута.

5. **`ShipmentAssignment` (`shipment_assignments`) — Назначение отправления на остановку**
    * Поля: `id` (PK), `shipment_id` (`FK -> shipments.id`, `ON DELETE CASCADE`), `stop_id` (`FK -> stops.id`, `ON DELETE CASCADE`), `status` (`CHECK (status IN ('ASSIGNED', 'IN_TRANSIT', 'DELIVERED'))`).
    * Ограничения: Уникальный ключ `uk_assignment_shipment (shipment_id)` гарантирует, что одно отправление не может быть одновременно назначено на несколько остановок или маршрутов.

## 2. Целостность данных, конкурентный доступ и защита переходов состояний

* **Защита переходов состояний:** Статусы сущностей (`Route`, `Shipment`, `ShipmentAssignment`) изменяются исключительно по правилам предметной области. Попытка передать новый `status` через `PATCH`-запрос отклоняется со статусом `409 Conflict`. Создание (`POST`) и обновление (`PATCH`) для `ShipmentAssignment` выполняются через сервисный слой с вызовом бизнес-операций назначения и переноса.
* **Согласованность при удалении:**
    * Удаление назначения, остановки или маршрута разрешено только пока маршрут находится в статусе `PLANNED` (попытка удалить маршрут в статусе `IN_PROGRESS` или `COMPLETED` вернет `409 Conflict`). При удалении планируемого маршрута, остановки или назначения все затронутые отправления автоматически возвращаются из статуса `ASSIGNED` в статус `CREATED`.
    * Удаление пользователя (`DELETE /api/users/{id}`) запрещено (`409 Conflict`), если у него есть активные отправления (не в статусах `DELIVERED` или `CANCELLED`).
* **Защита от гонок (Race Condition):** При проверке лимита веса и смене статусов маршрута и отправления используется пессимистическая блокировка на уровне БД (`@Lock(LockModeType.PESSIMISTIC_WRITE)` / `SELECT ... FOR UPDATE`). При переносе между двумя маршрутами блокировки берутся в детерминированном порядке `id` для предотвращения взаимоблокировок (`deadlock`).

## 3. Реализованные бизнес-операции

### 1. Назначение отправления на остановку маршрута с контролем веса и адреса
* **Эндпоинт:** `POST /api/routes/{routeId}/assign-shipment?stopId={stopId}&shipmentId={shipmentId}`
* **Затрагиваемые сущности:** `Route`, `Stop`, `Shipment`, `ShipmentAssignment`.
* **Правила и ограничения:**
    * Остановка должна принадлежать указанному маршруту, а адрес остановки должен совпадать с адресом доставки отправления.
    * Маршрут должен находиться в статусе `PLANNED`, а отправление — в статусе `CREATED`.
    * Под пессимистической блокировкой маршрута и отправления вычисляется суммарный вес назначенных посылок. При превышении `maxWeight` возвращается `409 Conflict`.
* **Результат:** Создается запись `ShipmentAssignment` (`ASSIGNED`), статус посылки меняется на `ASSIGNED`.

### 2. Запуск маршрута на линию
* **Эндпоинт:** `POST /api/routes/{routeId}/start`
* **Затрагиваемые сущности:** `Route`, `Stop`, `ShipmentAssignment`, `Shipment`.
* **Правила и ограничения:**
    * Маршрут должен быть в статусе `PLANNED`, содержать минимум одну остановку и минимум одно назначенное отправление.
* **Результат:** Статус маршрута переходит в `IN_PROGRESS`, а все привязанные назначения и посылки синхронно переводятся в статус `IN_TRANSIT`.

### 3. Выполнение доставки на остановке с контролем очередности
* **Эндпоинт:** `POST /api/stops/{stopId}/deliver`
* **Затрагиваемые сущности:** `Stop`, `Route`, `ShipmentAssignment`, `Shipment`.
* **Правила и ограничения:**
    * Маршрут остановки должен находиться в статусе `IN_PROGRESS`.
    * Проверяется соблюдение последовательности следования (`sequenceNumber`): курьер не может закрыть доставку на следующей остановке, пока не доставлены посылки на предыдущих по порядку остановках (`409 Conflict`).
* **Результат:** Назначения и посылки текущей остановки переводятся в статус `DELIVERED`. Если все назначения маршрута доставлены, `Route` автоматически переходит в статус `COMPLETED`.

### 4. Перенаправление (перенос) отправления на другую остановку/маршрут
* **Эндпоинт:** `POST /api/shipments/{shipmentId}/transfer?newStopId={newStopId}`
* **Затрагиваемые сущности:** `Shipment`, `ShipmentAssignment`, `Stop`, `Route`.
* **Правила и ограничения:**
    * Доступно только для отправлений в статусе `ASSIGNED`, пока исходный и целевой маршруты находятся в статусе `PLANNED`.
    * Адрес целевой остановки должен совпадать с адресом отправления (адрес посылки не перезаписывается).
    * При переносе на другой маршрут проверяется его остаточный лимит веса (`maxWeight`) под пессимистической блокировкой.
* **Результат:** Назначение перепривязывается к новой остановке, освобождая вес в исходном маршруте.

### 5. Отмена отправления клиентом
* **Эндпоинт:** `POST /api/shipments/{shipmentId}/cancel`
* **Затрагиваемые сущности:** `Shipment`, `ShipmentAssignment`, `Route`.
* **Правила и ограничения:**
    * Отмена запрещена, если посылка находится в статусе `IN_TRANSIT`, `DELIVERED`, `CANCELLED` или если маршрут уже запущен (`409 Conflict`).
* **Результат:** Посылка переходит в статус `CANCELLED`, а активное назначение удаляется, возвращая зарезервированный вес маршруту.

## 4. Базовые CRUD-эндпоинты

* **Пользователи:** `GET`, `POST`, `PATCH`, `DELETE` `/api/users`
* **Отправления:** `GET`, `POST (?senderId=)`, `PATCH`, `DELETE` `/api/shipments`
* **Маршруты:** `GET`, `POST`, `PATCH`, `DELETE` `/api/routes`
* **Остановки:** `GET`, `POST (?routeId=)`, `PATCH`, `DELETE` `/api/stops`
* **Назначения:** `GET`, `POST (?shipmentId=&stopId=)`, `PATCH (?newStopId=)`, `DELETE` `/api/shipment-assignments`

## 5. Инструкция по настройке и запуску приложения

### Требования к окружению
* **Java:** JDK 21
* **Maven:** 3.9+ (или встроенный Maven Wrapper `./mvnw`)
* **СУБД:** PostgreSQL 15+ (порт `5432`)

### Шаг 1. Подготовка базы данных и применение `init.sql`
1. Создайте в PostgreSQL базу данных `courier_db` от имени суперпользователя `postgres`.
2. Выполните SQL-скрипт `init.sql`, передав пароль для ограниченного пользователя `courier_app_user` через параметр `app_password`:

        psql -U postgres -d courier_db -v app_password='<ваш_пароль_бд>' -f init.sql

    * **Внимание:** скрипт `init.sql` содержит команды `DROP TABLE IF EXISTS ... CASCADE` для чистого пересоздания схемы и заполнения стартовыми тестовыми данными. Повторный запуск скрипта удалит существующие таблицы и пересоздаст их заново.
    * Скрипт создаст все таблицы, ограничения целостности (`CHECK`, `UNIQUE`, `FOREIGN KEY`) и ограниченного пользователя `courier_app_user` с правами только на `SELECT, INSERT, UPDATE, DELETE` и чтение секвенций (без прав `CREATE` / `ALTER`).
### Шаг 2. Настройка переменных окружения (`.env`)
Скопируйте шаблон `.env.example` в файл `.env` в корне проекта и укажите ваши параметры подключения:

    DB_URL=jdbc:postgresql://localhost:5432/courier_db
    DB_USERNAME=courier_app_user
    DB_PASSWORD=<ваш_пароль_бд>

### Шаг 3. Запуск сервиса
Выполните запуск через Maven Wrapper или из вашей IDE (класс `DostavkaApplication`):

    ./mvnw spring-boot:run

При старте Hibernate проверит схему БД в режиме `ddl-auto: validate` на полное соответствие JPA-сущностям. Сервис будет доступен по адресу `http://localhost:8080`.

## 6. Проверка API и запуск коллекции Postman

1. Откройте **Postman** и импортируйте файл `postman_collection.json` из корня проекта.
2. Запустите всю коллекцию целиком через **Run collection** (или выполняйте запросы последовательно сверху вниз):
    * **Папка «1. Сквозной сценарий и Бизнес-операции»** создает исходные сущности, автоматически сохраняет их ID в переменные коллекции и проводит полный жизненный цикл доставки: назначение посылок, проверку отказа при перегрузе (`409 Conflict`), проверку неизменности данных после отказа, перенос посылки на резервный маршрут, отмену посылки, запуск маршрута, проверку запрета отмены в пути (`409 Conflict`), проверку запрета нарушения очереди остановок (`409 Conflict`) и штатное завершение всех остановок с автоматическим переходом маршрута в статус `COMPLETED`.
    * **Папки 2–6 (CRUD по всем 5 сущностям)** проверяют операции создания (`201 Created`), чтения (`200 OK`), обновления (`200 OK`) и удаления (`204 No Content`) для каждой таблицы.
3. Каждый запрос в коллекции снабжен автоматическими тестами (`pm.test`), проверяющими HTTP-статусы и корректность состояния возвращаемых объектов.
